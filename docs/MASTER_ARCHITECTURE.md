# NOVA TAILS — Master Architecture v0.1

**Status:** REVIEW  
**Purpose:** Define durable boundaries and dependency principles before detailed product/content production. Product identity, concrete game/lore taxonomies and output priorities remain hypotheses until dedicated reviews.

## 1. Architecture model

Current Product Vision hypothesis is a distinctive original multi-species sci-fi/fantasy universe/IP, initially explored through character-centric concepts and potentially supporting multiple adaptations. Phase 0 does **not** approve that market/product hypothesis; it establishes how reviewed canon and adaptations should relate if retained.

```text
                 PROJECT / IP (working name)
                         |
                    REVIEWED CANON
                         |
          +--------------+--------------+
          |              |              |
        WORLD        IDENTITY        SYSTEMS
                         |
              MASTER ENTITY/CHARACTER IDENTITY
                         |
              ADAPTATIONS (optional)
             /          |          \
           GAME         2D          3D
```

No adaptation lane is automatically required to be a launch product. Product Vision decides priorities. Generated images/models are outputs, not source of truth. Originality/third-party-rights risk requires validation; it is not guaranteed by AI generation or this architecture.

## 2. Canon layers

### Universe Canon
Reviewed cosmology/history/world/faction/culture/conflict/terminology when those systems exist.

### Identity / Character Canon
Reviewed stable identities and retained constraints.

### Game Canon — conditional
Interaction/combat/progression/abilities/stats/equipment/enemies/economy/acquisition only if the game direction retains them and they survive review/prototype.

### Asset Canon
Reviewed visual/output standards. Manufacturing constraints become canonical only if physical collectibles remain in scope and are physically tested.

## 3. Candidate character architecture — DRAFT

Potential dimensions include origin, world identity, combat identity if applicable, progression if applicable, visual DNA and output adaptations. This is a stress-test model, not approved taxonomy. Individual dimensions must justify the decisions they enable.

Candidate terms/lists previously explored (Origin Domain, Organic/Mecha/Spirit/Arcane/Abyss/Celestial, classes, roles, elements) remain DRAFT.

## 4. Durable taxonomy principle

Avoid unnecessary coupling: if retained, species should not automatically determine combat class, and faction should not automatically determine species unless Product Vision/world design intentionally chooses such a constraint. Do not mass-populate candidate taxonomies before product/prototype review.

## 5. Durable progression/equipment principle

If progression/equipment exists, each retained system should create a distinct decision/unlock/job. Systems that only duplicate percentage stat inflation should be merged/removed. Current Level/Cultivation/Evolution/Skill/Equipment and Weapon/Armor/Accessory models are DRAFT only.

## 6. Durable interaction-data principle

Do not design exhaustive ability/stat schemas before a working prototype exposes actual behavior/data needs. Basic/Skill/Passive/Ultimate and detailed skill grammar are candidate vocabularies only.

## 7. Encounter principle — conditional

If the product/game uses enemies/bosses, they should teach/test mechanics and belong coherently to the world rather than functioning only as HP/stat bags. Existing subtype lists remain DRAFT.

## 8. Stable identity principle

Production identities should receive stable IDs once taxonomy/registry needs them. Example character ID format only: `NT-ORG-FOX-001`.

If forms/evolution remain part of the product, forms should inherit base identity rather than independently redefining it. Exact schema is intentionally deferred.

## 9. Cross-output identity principle

Adaptations may differ technically while preserving reviewed identity. If print is retained, visual effects/fine details may require physical reinterpretation; such examples are not manufacturing specifications.

## 10. AI generation architecture

```text
REVIEWED CANON
  ↓
Context Builder
  ↓
Prompt Template
  ↓
AI Proposal
  ↓
Validation
  ↓
Human Review
  ↓
Approved Canon / Asset Registry (when applicable)
```

Prompts are derived artifacts. Prompt text must never silently override canon.

## 11. Validation gates

Use only gates relevant to the artifact/system being reviewed:
- Identity: stable identity/locked features/signature.
- World/Game: reviewed constraints; placeholders remain marked.
- Visual: reviewed visual language and roster distinction.
- Print (conditional): part/color/geometry/support/build-volume and physical tolerance tests.
- IP risk: internal similarity review, external name/design research, provenance/human design history; formal legal review where commercial risk justifies it.

These processes reduce risk; they do not guarantee absence of third-party rights.

## 12. Production principle

Do not expand content simply because AI makes content cheap. Production begins only after a vertical slice or equivalent proof validates retained product assumptions and required pipelines.

## Phase 0 review boundary

Phase 0 can approve the **architecture/governance principles** in this document without approving proposed universe positioning, game format, world lore, taxonomy or physical-product role. Product Vision and subsequent evidence/prototypes decide those.
