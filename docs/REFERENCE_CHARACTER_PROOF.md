# NOVA TAILS — Reference Character Proof v0.1

**Status:** PROPOSED  
**Goal:** Stress-test the master asset architecture with one identity before scaling the roster.

## Why one character

The purpose is not to produce a flagship. It is to discover whether the identity/master/adapter boundaries are useful in real production.

Using multiple characters before the contract works would multiply migration cost.

## Candidate selection

Current experiment evidence is insufficient to promote Scout, Guardian, Spirit or Wild to production canon.

P01 exploratory feedback (`n=1`) provides useful issue discovery only:
- Scout and Guardian were perceived as related/evolution-like;
- Scout triggered a Pokémon association;
- Spirit was read as categorically different/non-normal-animal;
- Wild communicated a lean/speed/assassin-like fantasy and was selected for further interest;
- participant expressed interest in combination + upgrading as an interaction idea.

These observations are not representative demand evidence.

For architecture stress testing, a reference may remain `DRAFT`. Passing the architecture proof does not promote it to production canon.

## Preferred reference candidate

**Spirit direction** is the provisional architecture reference because its broken-orbit topology is structurally distinctive and should create meaningful adaptation challenges across 2D and physical form.

This is an engineering/reference choice, not a market ranking or flagship decision.

## Proof stages

### P0 — Identity contract
Create one schema-valid DRAFT identity instance with explicit invariants/adaptable properties.

### P1 — 2D adaptation
Produce a neutral primary depiction and one deliberately different pose/composition. Verify the broken-orbit/signature relationship survives both.

### P2 — Print adaptation design
Translate the same identity into a printable design plan. Document which visual details must be simplified, segmented or thickened. Do not invent universal tolerances.

### P3 — Dependency manifest
Record both adapters against the same identity revision. Simulate one upstream compatible refinement and one identity-breaking change; verify impact is understandable.

### P4 — Optional lightweight game representation
Only if it reveals a new architecture constraint: define gameplay-camera silhouette, animation/VFX ownership and signature preservation. No combat/economy design required.

## Architecture PASS criteria

- one master identity can drive two materially different outputs without duplicate authority;
- invariants are concrete enough for a reviewer to detect drift;
- medium-specific compromises can be recorded without polluting canon;
- dependencies identify which adaptations may be stale after upstream change;
- AI context can be derived from the same contract rather than manually re-describing the character each time.

## REVISE signals

- schema is filled with output-specific trivia;
- adapters need to overwrite master identity to function;
- invariants are vague adjectives rather than reviewable design constraints;
- every output needs a completely separate identity description;
- version/dependency rules create more bookkeeping than traceability.

## Scope boundary

This proof validates asset-system architecture only. It does not validate desirability, market demand, game fun, print demand, monetization or final IP originality/legal clearance.
